# Между парами

## Как начать рабочую сессию

1. Прочитать DEVELOPMENT_STATE.md и выполнить git status --short --branch.
2. Открыть нужный этап Development_Plan.md. Game_Design.md читать выборочно по текущей задаче.
3. Продолжить с записанного следующего шага; не повторять уже подтверждённые проверки без причины.
4. После работы обновить DEVELOPMENT_STATE.md: что работает, чем проверено, ограничения, следующий шаг. Держать его кратким; не копировать туда диалоги и большие логи.

## Границы проекта

- Первая игра охватывает весь первый курс. Системы и баланс не менять без связи с задачей пользователя.
- Проект Unity находится в Unity/. Документы лежат в корне.
- Код и подключение систем — технический разработчик. Графика, звук, окружение, сценарии и тестовые прохождения — разработчик контента.
- Не добавлять сетевые сервисы, монетизацию и новые игровые подсистемы по собственной инициативе.

## Реализация и проверка

- Перед редакторскими действиями использовать Unity CLI и соответствующие Unity skills. Сцены, префабы и настройки менять через Unity API.
- Вместе с каждым новым исходником или ассетом коммитить его .meta, сгенерированный Unity. Не добавлять Library, Temp, Logs, UserSettings и сборки в Git.
- Использовать постоянные ID для игровых данных, когда появятся занятия и события. Одно выполнение действия должно выдавать награду ровно один раз.
- Не выдавать статический анализ за прохождение: отдельно указывать компиляцию, автоматические проверки, проверку в Play Mode и запуск сборки.
- Не перезаписывать чужие изменения и не менять основную ветку принудительно. Делать небольшие понятные коммиты.
